🎯 Trade Decision Engine model …UNCALIBRATED PRIOR

Per-event go/skip scorer: a bot sees price entering a zone, fires one POST /api/trade-decision/decide, and gets probability + direction + size in milliseconds. Slow loop maintains per-pair feature snapshots; fast loop is a pure dot-product. Design: Trade_Decision_Engine/ARCHITECTURE.md · Live ticking version: continuation-fade-ticker.html

How to use

  1. Pick a pair and mode. synthetic works anywhere (deterministic demo data, no OANDA needed — the sandbox default). live needs the server to have OANDA_KEY (Railway) — nothing else: Decide warms its own snapshot on the first call (a couple of seconds, then ms). The ⟳ Refresh button just forces a fresh one — worth pressing right before an actual entry.
  2. Load the snapshot (σ, regime, trend-day-ness T, vol percentile, level map). What is a zone? The engine builds it automatically: it collects levels from the pluggable sources — daily opens, prior day/week high–low, pivots, swing S&R, multi-swing fib clusters, round numbers — and merges any that sit within ~0.08σ of each other into one zone with a confluence count (how many distinct sources agree) and a weighted score. You never define zones by hand; the table IS the map. Click a zone row to load its price into the decide form, simulating "price is touching this zone now".
  3. Decide. Leave action/direction on auto to let the engine derive them from the day-type selector, or set them to make the engine judge your proposal. approach σ simulates how fast price came into the level (in σ units — 1.5 = freight train). Your own level: tick my own level to score a price the map doesn't know (your hand-pulled fib, an order-flow line). If the map has a zone there anyway, it's used — your level agreeing with the map counts as confluence; if not, it's scored as a standalone external level rather than refused.
  4. Read the result: GO/SKIP, the probability, the size dial, and why (top factors, hard-gate reasons). Every call is appended to the decision log below — that log is the future training set for the fitted (calibrated) model.
Bot integration is the same call:
curl -s -X POST $HOST/api/trade-decision/decide -H 'content-type: application/json' \
  -d '{"pair":"eurusd","price":1.0852,"approach_sigma":0.4,"mode":"live"}'
# → {"decision":"go","direction":"short","action":"fade","probability":0.61,"size_multiplier":0.8,...}

    API reference
    
  
    POST /api/trade-decision/decide          { pair, price?, action?, direction?, approach_sigma?, mode? }
GET  /api/trade-decision/state/:pair     ?mode=synthetic — inspect the snapshot the fast loop reads
POST /api/trade-decision/refresh         { pair } | { pairs:[...] } — run the slow loop (needs OANDA)
GET  /api/trade-decision/log             ?limit=50
GET  /api/trade-decision/health          model version + snapshot staleness per pair
POST /api/trade-decision/backfill/run    { full?, gap_fill?, macro? } — macro:false = baseline mode
POST /api/trade-decision/macro-verdict/run   compute the #7 verdict over the event log
GET  /api/trade-decision/macro-verdict       last verdict (bucket test + ablation + frozen bar)

Hard gates (fail-closed, probability=null): no_snapshot · stale_features · news_window · no_level_nearby
Auto slow loop in Railway: set TDE_PAIRS=eurusd,gbpusd,usdjpy (+ TDE_REFRESH_MIN, default 5)
    
  
    Honesty box: the v0 model is a hand-weighted prior, not evidence — every response carries calibrated:false. It becomes a real meta-labeled model only after the decision log accumulates outcomes and a walk-forward fit proves OOS calibration (≥30 events per bucket). See ARCHITECTURE.md §7/§9.
