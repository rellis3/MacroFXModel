🚀 Day one — bootstrap from Oanda history ⏱ 10–20 sec
Fetches ~13 days of H4 bars from Oanda (80 bars per pair), runs rolling beta estimation across those bars, classifies regime per window using EMA crossover, and derives targets immediately. Run this as soon as the bot is deployed.
# Preview first — see derived targets without pushing anything
python RegimeV2/beta_regime_table.py --backfill --dry-run

# Push regime table + update beta targets in KV
python RegimeV2/beta_regime_table.py --backfill --update-targets --url https://your-worker.workers.dev

# Double the history window (~26 days) for more regime diversity
python RegimeV2/beta_regime_table.py --backfill --bar-count 160 --update-targets --url https://your-worker.workers.dev

# Also save the synthetic records to beta_history.jsonl for future runs
python RegimeV2/beta_regime_table.py --backfill --save-backfill --update-targets --url https://your-worker.workers.dev
🔄 After weeks of live data — rebuild from real history ⏱ <2 sec
Once the bot has been running long enough to accumulate 30+ records per regime in bot/data/beta_history.jsonl, drop --backfill entirely. These targets will be more accurate because regime labels come from the actual HMM.
# Standard rebuild — derives targets from live history only
python RegimeV2/beta_regime_table.py --update-targets --url https://your-worker.workers.dev

# Require more samples per regime for higher-quality targets
python RegimeV2/beta_regime_table.py --update-targets --min-samples 50 --url https://your-worker.workers.dev

# Practice/demo Oanda account
python RegimeV2/beta_regime_table.py --backfill --oanda-practice --update-targets --url ...

# OANDA_KEY can also be passed as env var instead of --oanda-key
OANDA_KEY=your_key python RegimeV2/beta_regime_table.py --backfill --update-targets --url ...

Volatility Bot — per-line fade
Fades the vol-forecast Proj-H/L bands on the approach-velocity edge · survivor universe + frozen policy from the per-line book · triple-barrier exit · volatility_bot/volatility_bot.py
▸ How the bot decides & what each status means (read this if the table looks confusing)
The day, start to finish
  1. Plan publishes once a day (~23:05 UTC). It freezes today's survivor pairs, each pair's σ/open, the band fractions, and the fade/follow/skip policy — the bot never re-learns intraday.
  2. The session runs London midnight → 22:00 close. Eight lines per pair are watched the whole time: Close (OC50/OC75) sit static off the open; Proj-H/L (HL50/HL75) trail the running low/high, so they drift during the day.
  3. When price touches a line, the decision engine reads ONE policy cell — keyed by which line × how fast price approached (grind / med / spike) — and returns fade, follow, or skip.
  4. fade/follow → enter at the line immediately. skip → no trade, and the line is marked done.
  5. One decision per line per session. Once a line is decided (traded OR skipped) it is never re-evaluated — price can sit beyond it without re-firing.
Reading the statuses
  • Acted ≠ traded. The Acted column lists every line decided this session — including skips. A line shows as acted whether the engine faded it or rejected it as not worth the cost. So a busy Acted list with 0 open positions is normal.
  • ▶ green badge / Open Positions table = a line the bot is actually holding right now. That is the only place a live trade shows.
  • Open positions counts live trades; Today's trades counts trades already closed today (they move to the Positions → Trade History audit).
Exit — mechanical, not discretionary

A trade exits on a fixed triple barrier, set at entry and never second-guessed: a fade takes profit at the inner line (toward the open) and stops out at the outer line (further away); a follow is the reverse. The bot does not watch a live trade and decide "this is reverting, get out" — there is no mid-flight re-read. It either hits its target line, hits its stop line, or is still open at session close.

Why the Close (OC) lines rarely trade

OC lines aren't excluded — each is judged the same way. The reason isn't spread (that's ~1 pip and trivial): it's expectancy. A fade takes profit at the near line and stops at the far line, so on the inner OC bands the trade often risks more than it targets (reward:risk < 1). To pay, price has to revert off the Close line often enough to beat that ratio — and it doesn't: in a trending push price runs through the close line to the next band. So the average is a loss even though each winner looks fine — exactly the "small wins, big losses" pattern. In the honest, cost-aware out-of-sample book those cells come back skip; a gross/in-sample backtest that ignores this does "trade" them, which is why they looked tradeable there.

Every decided line now shows its verdict in the Decided — why column (hover for the cell's expectancy, reversion rate and sample count), so you can see per line whether it was traded, skip · edge < cost, skip · too few samples, or an unseen line×speed combo.

This is bot-side state, not something the server plan can carry, because it depends on this bot's own fills.

Fade-stop tightening

Applied by the SERVER when it builds the plan — a fade zone's stop may already be tightened toward entry using that pair's own historically-validated MAE percentile. There's nothing for the bot to recompute; the toggle below just controls whether the server applies it.

Fib Atlas Bot — Asia + Monday range-extension vote
Two independent ladders (Asia session range, Monday full-week range), each pair can carry BOTH at once · fade/follow vote at each rung's touch, priced against the real fib-extension distances · chandelier ATR trailing stop manages the exit live · fib_atlas_bot/fib_atlas_bot.py
▸ How the bot decides & what each status means (read this if the table looks confusing)
The day, start to finish
  1. The server refreshes a plan (fib_atlas_bot_plan) roughly every 45 seconds — one entry per (pair, ladder) currently-armed rung, each already voted (fade/follow) and priced (entry/SL/TP) against the real fib-extension distances. The bot never re-derives a vote or a level — the plan does.
  2. The bot watches live price against each zone's entry. A rung's "armed" state (whether a touch right now counts as a fresh, re-armed entry vs. a rung still cooling down from an earlier touch today) is tracked bot-side — the plan tells the bot the CURRENT decision/margin for that rung, the bot tracks WHEN price actually crosses it.
  3. One pair can hold an Asia position AND a Monday position at once — they're independent bets on the same instrument, not duplicates. The bot's dedupe tag keeps the two ladders from colliding with each other or with themselves.
  4. Before every entry the bot checks, in order: kill switch → plan freshness → daily/monthly drawdown lockout → drawdown throttle → duplicate/stack guard → spread cap → portfolio risk budget.
  5. Once open, the position's stop trails via a chandelier ATR stop (Asia 3× ATR, Monday 1.5× ATR, both on a 60-bar M1 ATR) — only ever tightening in the favorable direction, never loosening.
Sizing vs. the actual bracket stop

A fade zone's actual broker stop (sl) may already be tightened by the server beyond the full stop distance (sizingSl). Position sizing ALWAYS uses the full, untightened distance — sizing off a tightened stop would size the position UP to compensate, which is leverage in disguise, not a real edge improvement.
