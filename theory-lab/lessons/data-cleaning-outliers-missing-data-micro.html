Data Cleaning, One Failure Mode at a Time

The data-pipeline lesson before this one named cleaning as Stage 3 — the step that fixes whatever validation flagged — without saying how. Here's how: a fat-finger print, a stale quote, a trading halt, and a genuine gap are four different problems that look similar on a chart and need four different fixes, and the single easiest way to get any of those fixes wrong is the same lookahead-bias mistake the feature-engineering-and-leakage lesson warned about — cleaning a data point using statistics that peek at data from after it happened.

Section 1

Four failure modes, four different signatures

Each one shows up in real feeds routinely. None of them is fixed the same way.

⚡

Fat-finger print

A single trade or quote at a wildly implausible price — an extra zero, a misplaced decimal — that snaps straight back to normal on the very next tick.

🧊

Stale quote

The feed connection stays technically "up," but the price stops refreshing — repeating the same value while the real market keeps moving underneath it.

⛔

Trading halt

A real event — a circuit breaker, a scheduled closure — where prints genuinely stop and then resume, often at a meaningfully different level.

▢

Genuine data gap

Prints are simply absent — a dropped connection, a vendor outage — with no guarantee the market did or didn't move while nothing was recorded.

The trap is treating these as one problem — "weird data" — and reaching for one universal filter. A fat-finger print is an error to remove. A halt is a real event to represent honestly, not "fix." Confusing the two corrupts the series either way.
Section 2

What the raw data looks like, and the correct fix

Same-looking "gap in the chart" — four different underlying causes, four different correct responses.

Try it
Raw: a single isolated print far from both neighbors, correcting itself immediately. Fix: a causal rolling median/MAD check flags it the instant it prints — no future ticks needed — then it's replaced or excluded as the single bad point it is.
Raw: the connection never drops — the feed just repeats the same price while the market keeps moving. Fix: a "hasn't changed in N periods" check on the raw print catches this — an outlier-on-price-level filter won't, because the stale value isn't extreme, it's just frozen. Treat the stale stretch as missing, not as N real observations.
Raw: prints genuinely stop, then resume — often at a meaningfully different price, a real jump either side of the gap. Fix: represent it as missing, honestly. Never "correct" the resumption jump toward a smooth path — a naive outlier filter or a blind interpolator will try to, and both are wrong here.
Raw: data is simply absent, with no guarantee the market moved or held still underneath. Fix: no universal default — forward-fill, interpolate, or flag-and-exclude, chosen deliberately based on gap length and what's built on top (Section 5).

Section 4

One universal filter breaks on at least one of these

One blanket outlier filter
  • Flags the halt's resumption jump as an "error" and smooths it toward the pre-halt level — destroying a real, if wide, price move
  • Misses the stale quote entirely — the frozen value isn't extreme, so a price-level check sees nothing wrong
  • Can flag a genuinely large but real move (a scheduled data release) as bad, deleting real information
  • Applies the same threshold everywhere, regardless of why a value looks unusual
Matched detection per failure mode
  • A causal rolling median/MAD check for isolated spikes — Section 2's fat-finger tab
  • An explicit "unchanged for N periods" check for staleness — a different question from "how extreme is this value"
  • A halt/gap calendar or a no-prints check flags the genuine break, and it is never run through the outlier filter at all
  • A deliberate fill-or-exclude decision, made per gap, once it's clear which failure mode produced it
Why this needs four tools, not one

Detection has to ask the right question for the right failure. "Is this price extreme?" catches a fat finger. "Has this stopped moving?" catches a stale quote. "Are there any prints at all?" catches a halt. One threshold on one statistic cannot answer three different questions correctly at once.

Section 5

Detecting a spike without being fooled by it

The standard tool for the fat-finger case: robust statistics that the outlier itself can't distort.

Mean & standard deviation

A single huge outlier drags the mean toward it and inflates the standard deviation — the exact yardstick used to judge "how extreme is this tick" is itself distorted by the tick being judged. The full lesson's worked example: a fat finger sitting at a real, locally enormous deviation can measure as only ~4.2 full-sample standard deviations once two years of other volatile days have widened that same standard deviation — just inside a 5σ threshold, uncaught for two years.

Rolling median & MAD

The median and the median absolute deviation (MAD) barely move even when a handful of values are extreme — computed causally, from data up to and including the current point, never later. On six illustrative ticks with one spurious print, the rolling median of the four prior points is 1.02 and the rolling MAD is 0.005; the spurious 4.50 print sits roughly 696 MADs away — flagged instantly, using nothing but data already available at that moment.

This deck's slider and calculator below use a simpler mean/standard-deviation z-score, on purpose — it's the fastest way to feel the "causal, not full-sample" discipline hands-on. Production spike detection prefers median/MAD for exactly the robustness reason on the left.

Section 8

The mandatory pitfall: cleaning with tomorrow's data

A good copy editor reads sentence by sentence, flagging a word that looks wrong given only what's been read so far. A bad editor reads the whole book first, then "fixes" a word in Chapter 2 using word choices the author only settles on in Chapter 20 — technically thorough, but dishonest about what a reader at that point could actually have known. "Remove anything more than 5 standard deviations from the full-sample mean" is the second editor: the mean and standard deviation it uses were computed with knowledge of every future extreme value in the series.
The exact overlap with feature-engineering leakage

This is the identical failure mode the feature-engineering-and-leakage lesson describes for a feature z-scored against a full-sample mean and standard deviation instead of only-past statistics — the same underlying rule (never let time index i's computation see data from after i) applied one stage earlier: cleaning the raw series here, versus building a feature from an already-clean series there. A live pipeline processing ticks one at a time as they arrive could never reproduce a full-sample cleaning decision — it has no way to know the full-sample statistics until the sample is complete, which by definition is after every row in it has already happened.

This is exactly why the slider and calculator above are wired to causal, only-past statistics rather than the whole illustrative dataset — it's the same discipline this pitfall demands, made concrete instead of abstract.

Section 9

Filling a gap: three honest options, three real failure cases

Once something is flagged bad or absent, deciding what fills it is a separate decision from detection — and none of the three is a safe universal default.

→

Forward-fill

Repeat the last known value. Reasonable for a short gap in an illiquid instrument. Fails badly across a real event: a halt or stale stretch forward-filled manufactures a flat, zero-return period that a volatility or trend feature reads as authentic calm.

∿

Interpolation

Draw a line between the last known-good value and the next one. Reasonable for a very short, clearly spurious single-tick gap. Fails across a longer gap: it invents a smooth path, when a halt often resumes at a sharp, discontinuous level nowhere near that average.

⊘

Flag and exclude

Mark the period missing and leave it out of any calculation. The most honest option — it never manufactures data. Fails if applied too liberally on routine short micro-gaps: it shrinks the usable sample for no real benefit.

Where this needs qualifying

Detection and handling are genuinely separate questions. Flagging a value as bad or missing says nothing about what — if anything — should replace it; conflating the two hides a tradeoff that has to be made deliberately, gap by gap.

Section 10

Check yourself

Nothing is scored beyond this device. The explanation is the useful part.

Question 1

What makes a stale quote harder to catch than an outright feed disconnect?

A disconnect shows up in connection status directly. A stale quote leaves the connection technically up while prices stop refreshing — only a check on whether the value has actually changed can catch it.
Question 2

Why is median/MAD preferred over mean/standard deviation for spike detection?

A single huge outlier drags the mean toward it and inflates the standard deviation — the very yardstick used to judge extremity. The median and MAD are robust: a handful of extreme values barely shifts either one.
Question 3

A halt causes a real, sharp jump when trading resumes. What's the correct way to treat that jump?

A halt is a genuine market event. The resumption jump is real information, not a data error — "fixing" it toward a smoother path destroys information a fat-finger filter or interpolator would wrongly overwrite.
Question 4

x = 112, causal mean = 100, causal std = 4, threshold k = 3. What's the z-score, and is it flagged?

z = (112 − 100) ÷ 4 = 3.0. With the flag rule "|z| exceeds k," a z of exactly 3.0 against k = 3 sits right on the boundary and is not flagged — a reminder to check whether a real system's rule is strictly-greater-than or greater-or-equal.
Question 5

Why is "remove anything >5σ from the full-sample mean" a lookahead-bias bug?

A live pipeline cleaning ticks as they arrive could never reproduce a full-sample decision — it has no way to know the full-sample mean/standard deviation until the sample is complete, which is after every point in it already happened. Same failure mode as a feature z-scored on full-sample statistics.
Section 11

What to carry forward

01

Four distinct failure modes need four distinct fixes — a fat-finger print, a stale quote, a halt, and a genuine gap are not the same problem, even when they all look like "something's wrong with this data."

02

Robust statistics resist being fooled by their own target — median/MAD barely moves when a handful of values are extreme, unlike a mean/standard-deviation pair.

03

Detection and handling are separate decisions — flagging a bad value says nothing about what, if anything, should replace it.

04

Every missing-data strategy has a real failure case — forward-fill fakes calm, interpolation invents a path, flag-and-exclude shrinks the sample.

05

Cleaning must be causal — a statistic used to judge whether a point is bad may only use data available up to that point, never data from after it. Full-sample cleaning is a lookahead-bias bug, the same failure mode leakage warnings describe for features.

06

Log every cleaning decision — an unrecorded fix is indistinguishable from silent corruption once enough time has passed.

What this now lets you do

Look at a "weird" tick and immediately ask which of the four failure modes it actually is, rather than reaching for one universal filter. Build or audit a cleaning step that only ever uses data available up to the point it's judging. Spot a "full-sample 5-sigma" style filter as a lookahead bug on sight — the same discipline that matters for features, one stage earlier in the pipeline.
