Data Architecture for Systematic Trading: Storage, Versioning & Reproducibility

The infrastructure layer underneath every other lesson in this category — how historical data is stored, why independently-recomputed "single sources of truth" quietly drift apart, and why a pipeline bug and a genuine strategy decay can look statistically identical from the equity curve alone.

TL;DR
  • Time-series-oriented storage vs. general columnar storage: Parquet-style columnar formats are the modern practitioner-standard for large historical tick/bar datasets — fast columnar reads, efficient compression, schema evolution support.
  • The "single source of truth" principle: multiple pipelines or teams independently recomputing the same adjusted series will drift apart over time — a real, well-known organizational failure mode, not just a technical one.
  • Data lineage / audit trails: being able to answer, months later, "exactly which raw inputs and which code version produced this specific historical value."
  • Schema versioning: a pipeline's output schema changing over time without a version tag silently breaks anything downstream that assumed the old shape.
  • This lesson is the infrastructure The Research Pipeline: Hypothesis to Honest Backtest assumes exists when it talks about reproducibility — and it connects directly to the same theme in Feature Engineering, Leakage & Reproducibility.
  • A pipeline bug and a genuine strategy-alpha decay can look statistically identical from the equity curve alone — reproducible, versioned data lineage is the only way to rule the pipeline out first.
Section 01

Why this matters

Every earlier lesson in this category — ingestion and bar construction, cleaning, corporate-action and roll adjustment, point-in-time serving — produces a value that eventually has to live somewhere, be trusted by more than one consumer, and be reproducible later. This lesson is that underlying layer: not a new stage in the pipeline, but the architecture that makes every earlier stage's output durable, auditable, and safe to build on for more than one project at a time. The Research Pipeline: Hypothesis to Honest Backtest discusses reproducibility as part of a disciplined research process — pinning data, code, and parameters together so a result can be regenerated later. That discussion implicitly assumes a data architecture capable of actually delivering a pinned, specific historical vintage on demand; this lesson is what has to exist underneath it for that assumption to be true. It connects just as directly to Feature Engineering, Leakage & Reproducibility's point that "the data hasn't changed since I ran this" is rarely actually true without deliberate versioning — this lesson is the concrete architecture that claim depends on.

💡
Plain-English intuition

Two accountants, two spreadsheets, one company

Imagine two accountants at the same company, each independently maintaining their own spreadsheet of "adjusted revenue" for the same set of historical years, each applying similar but not identical correction rules by hand. For the first year or two, the two spreadsheets agree closely — the corrections are small and the underlying data is fresh in everyone's memory. Three years later, after a dozen small judgment calls in each spreadsheet that were never written down or reconciled against each other, the two numbers for the same historical year have quietly diverged, and nobody can say with confidence which one is right, or even exactly why they differ anymore. Neither accountant did anything obviously wrong in isolation — the failure is that there were ever two independently maintained "sources of truth" for the same fact in the first place, with no shared, versioned record of exactly what inputs and rules produced each number. A data architecture with a genuine single source of truth and a real audit trail is the fix: one authoritative, versioned pipeline that everyone reads from, with a permanent record of exactly what produced every historical value.

Section 02

Storage: time-series-oriented vs. general columnar formats

Historical tick and bar data has a specific shape: very long, mostly-numeric columns (price, volume, timestamp), queried far more often by "give me a date range for these few columns" than by "give me one full row." Traditional row-oriented storage (reading an entire record, all its columns, to get at just one or two of them) is a poor structural match for that access pattern. Columnar formats — Parquet-style storage being the modern practitioner-standard for large historical datasets — instead store each column's values contiguously, which brings three concrete practical benefits for this use case:

⚡

Fast columnar reads

A query that only needs the close price and timestamp over a date range reads only those columns, not every field in every row.

🗜️

Efficient compression

Values within one column (e.g. a price series) tend to be similar to their neighbors, which columnar layouts compress far better than mixed row-oriented data.

🧬

Schema evolution support

A well-designed columnar format can add a new column to future files without breaking a reader that only expects the old columns — a genuine, structural version of the schema-versioning discipline discussed below.

None of this makes columnar storage universally "correct" — a system that needs to append single new ticks continuously and read them back immediately has different needs than one built to serve large historical backtests — but for the specific job of storing and repeatedly querying large historical tick/bar archives, columnar formats have become the practitioner default for good, concrete structural reasons, not merely current fashion.

🧒 Explain like I'm 5

Imagine a filing cabinet full of forms, and you only ever want to know everyone's birthday, never their whole file. Row-oriented storage means pulling out every single person's entire folder just to read one line off each. Columnar storage is like keeping a separate stack that's nothing but birthdays, already lined up together — you grab exactly what you need, and similar values sitting next to each other also compress down smaller, the same way a page that just says "1985, 1985, 1986, 1985" squishes down easier than a page mixing birthdays with addresses and phone numbers.

Section 03

Single source of truth: why independent recomputation drifts

The "single source of truth" principle states that any given derived quantity — an adjusted close, a cleaned tick series, a continuous futures contract — should be computed by exactly one authoritative pipeline, with every downstream consumer reading its output, rather than each consumer (or each team) independently recomputing the same quantity from the same raw inputs. This sounds obvious stated abstractly, and it is nonetheless one of the most common real organizational failures in data engineering, for a specific reason: two independent implementations of "the same" computation virtually never stay bit-identical over time. A rounding convention chosen slightly differently, an edge case handled slightly differently, a bug fix applied to one copy and not the other, a corporate action or roll handled with a marginally different adjustment method — any one of these, applied inconsistently across two supposedly-equivalent pipelines, causes a slow, silent divergence. Neither copy is necessarily "wrong" in isolation; the failure is that there were ever two copies of the same authoritative computation running independently at all.

The trap: "our two systems compute adjusted close the same way" is a claim that is almost never actually re-verified after the initial build — it's assumed true because it was true on day one, and small, individually reasonable changes to either copy over months or years are what actually cause the drift, not any single dramatic error.
🧒 Explain like I'm 5

It's like two roommates each keeping their own separate shopping list for the same shared kitchen instead of one list taped to the fridge. At first the two lists match, because they started from the same groceries. But every time one roommate crosses something off slightly differently, or adds a substitute item the other doesn't know about, the two lists quietly stop matching — and neither roommate did anything crazy, they just each kept their own copy of something that should have only ever had one copy.

Section 04

Data lineage, audit trails, and schema versioning

Data lineage / audit trails

Lineage is the ability to answer, for any historical value sitting in the store today, exactly which raw inputs and which version of the transforming logic produced it — not approximately, but specifically enough to regenerate the exact same value from scratch. Without this, a value that looks suspicious months later (an unexpected spike, a value that doesn't match an external source) has no reconstructable history: there's no way to determine whether it reflects a genuine market event, a since-fixed bug that produced a since-corrected version elsewhere, or a raw input that was itself later found to be bad.

Schema versioning

A pipeline's output schema — which columns exist, what units they're in, what a null value means — changes over time as the pipeline is improved: a column gets renamed, a unit changes from basis points to a decimal fraction, a new field gets added. If that change isn't tagged with an explicit version, anything downstream that was built assuming the old shape breaks silently — not with an error, necessarily, but by quietly misinterpreting the new data as if it still meant the old thing. A renamed or reunit-ed column that isn't versioned is a classic, silent-failure source of exactly the kind of corruption this whole category is about.

🧒 Explain like I'm 5

Data lineage is a receipt trail — like being able to prove exactly which store, which cashier, and which day produced a specific item in your fridge, instead of just having the item with no memory of where it came from. Schema versioning is a label change notice — if the recipe box that used to hold "ounces" suddenly starts holding "grams" with no new label, anyone still reading it as ounces will cook something completely wrong without ever getting an error message.

🧮
Worked example

A silent schema change: units drift from basis points to a decimal fraction

Suppose a "spread" column has always been recorded in basis points — a typical FX spread reading might be \(1.8\) (meaning 1.8bp). A pipeline update changes the column to record the spread as a decimal fraction instead — the same 1.8bp spread is now recorded as \(0.00018\) — because a new team member reasonably thought a fraction was the more standard unit, and updated the column in place without adding a version tag or renaming the column.

A downstream cost model that reads this column and was built assuming basis points now silently multiplies every trade's assumed cost by roughly \(1.8/0.00018 = 10{,}000\times\) too small — treating a spread of 1.8 (old convention, basis points) as if a "spread" of \(0.00018\) meant something 10,000 times tighter than intended. The backtest doesn't error out; it simply becomes dramatically, silently optimistic about transaction costs from that date forward, because nothing in the pipeline's output signaled that the column's meaning had changed. A schema version tag on the column (or a rename to spread_frac alongside the old spread_bp) would have made this an explicit, visible break instead of an invisible one.

🎯
A real-world trading scenario

Two teams, two "adjusted close" columns, two years of silent drift

A research team and a risk team at the same shop each maintain their own pipeline for computing a daily adjusted close for a universe of instruments — the research team's copy feeds backtests, the risk team's copy feeds position and exposure reporting. Both started from the same raw feed and the same corporate-action logic, and for the first several months the two numbers matched exactly. Over the following two years, the research team's pipeline picked up a bug fix for how it handles a rare zero-volume day, and the risk team's pipeline separately picked up a change in how it rounds a dividend-adjustment factor — each change reasonable and correctly reviewed in isolation, in its own team's context, with no shared review process that would have compared the two pipelines' outputs against each other.

Two years later, a discrepancy surfaces: a strategy's backtested P&L (built on the research team's adjusted close) doesn't reconcile with the risk team's reported exposure for the same position on the same date, off by a small but real amount that compounds meaningfully over a long enough history. Both teams' numbers are individually defensible — each followed a sensible internal logic — but there is no single source of truth to check against, and reconstructing exactly when and why the two series diverged takes real forensic effort precisely because neither pipeline kept an explicit, versioned record of every change applied along the way. This is the single-source-of-truth failure mode made concrete: not a dramatic single error, but two individually reasonable pipelines slowly drifting apart with no shared reference to catch it.

Section 05

How practitioners actually use this

Institutional data engineering teams treat storage format, single-source-of-truth ownership, lineage, and schema versioning as infrastructure decisions made once and enforced organizationally, not re-litigated per project: one team or system owns each authoritative derived series, every consumer reads from it rather than recomputing it, every transform stage is tagged with the code version that produced its output, and every schema change ships with an explicit version bump that downstream readers can detect and react to. None of this is exotic engineering — it's the same discipline any mature software system applies to its own internal APIs, applied specifically to historical market data, because the cost of getting it wrong compounds silently for years before it surfaces.

⚠️
Common pitfalls

Where data architecture quietly breaks down

  • Letting more than one pipeline independently compute "the same" adjusted series. Even with identical starting logic, two independently maintained copies will drift — the single-source-of-truth principle exists specifically to prevent this.
  • Changing a column's meaning or units without a version tag. A silent unit or shape change doesn't error — it silently misleads anything downstream that assumed the old meaning, exactly like the basis-points-to-fraction example above.
  • Treating storage format as a purely technical, no-consequence decision. The wrong storage layout for the actual access pattern (row-oriented storage for a workload that's almost entirely column-range queries) has real cost and performance consequences at scale.
  • Assuming reproducibility without ever testing it. A team that believes "we could regenerate any historical value if we needed to" but has never actually tried doing so for a real historical value is assuming, not verifying, that its lineage is actually complete.
  • Diagnosing a performance decline as pure alpha decay without first ruling out a pipeline bug. See the closing illustration below — the two look identical from an equity curve alone.
The closing illustration: a genuine, honest strategy-alpha decay and a silent data pipeline bug can produce the exact same signature — a performance curve that quietly, gradually gets worse over time, with no single dramatic break to point to. From the equity curve alone, these two causes are statistically indistinguishable: both look like "the strategy just isn't working as well lately." The only way to tell them apart is having reproducible, versioned data lineage good enough to regenerate the exact historical inputs that produced each period's results and rule the pipeline out first — confirming the same raw inputs, the same code version, and the same schema were actually in effect throughout the period in question, before concluding the decline is real, economic alpha decay rather than a slow, undetected pipeline problem.

If your car starts getting worse gas mileage, that could mean the engine is genuinely wearing out — or it could mean your gas gauge is broken and lying to you. From the dashboard alone, both look exactly the same: the number just keeps getting worse. The only way to tell them apart is to actually check the engine and the gauge separately, not just stare harder at the dashboard. Same idea here — you have to check the data pipeline itself, not just squint at the declining performance chart.

Section 07

Self-test

Q1. Why is columnar storage a better structural fit than row-oriented storage for large historical tick/bar datasets?
Historical tick/bar data is typically queried by "give me a date range for these few columns" (e.g. close price and volume over a period) far more often than by "give me every field of one full row." Columnar storage keeps each column's values contiguous, so a query only has to read the specific columns it needs rather than loading every field of every row — this also compresses better, since values within one column tend to be more similar to their neighbors than a mixed row of different fields would be.
Q2. Why does the single-source-of-truth principle matter even when two independent pipelines both start from correct logic?
Two independently maintained implementations of "the same" computation virtually never stay bit-identical over time, even if both were correct on day one. Small, individually reasonable changes — a rounding convention, an edge-case fix, a slightly different adjustment method — applied to one copy and not the other accumulate into a real, silent divergence, with neither copy necessarily being "wrong" in isolation. The failure is structural: there were ever two independently maintained authoritative copies of the same derived quantity at all, with no shared reconciliation to catch the drift.
Q3. In the basis-points-to-fraction worked example, why did the cost model fail silently instead of erroring out?
The column's name and general shape stayed the same (a numeric "spread" field), so nothing in the pipeline's structure signaled that its unit convention had changed from basis points to a decimal fraction. A downstream cost model built assuming the old unit simply kept reading the new values as if they meant the old thing, producing a wildly understated cost estimate without any error, exception, or obviously broken output — exactly the kind of silent corruption an explicit schema version tag (or a distinctly-named new column) would have converted into a visible, catchable break instead.
Q4. What does "data lineage" let a team do, months after a value was first computed, that they couldn't do without it?
Lineage lets a team determine, for any specific historical value, exactly which raw inputs and which version of the transforming code produced it — specifically enough to actually regenerate that exact value from scratch. Without it, a suspicious-looking historical value has no reconstructable history: there's no way to determine whether it reflects a genuine market event, a since-fixed bug whose correction only propagated to some downstream consumers, or a raw input later found to be bad — the team is reduced to guessing rather than verifying.
Q5. Why can't a declining equity curve alone tell you whether a strategy's edge is genuinely decaying or whether a data pipeline bug is the real cause?
Both a genuine, honest alpha decay and a silent pipeline bug (a slowly drifting adjusted-close series, an unversioned schema change quietly corrupting an input, two independently recomputed sources diverging) produce the same visible signature: performance that gradually gets worse over time with no single dramatic break. The equity curve on its own carries no information distinguishing "the market behavior this strategy exploited has genuinely weakened" from "the data feeding this strategy has quietly become wrong." The only way to tell them apart is to use reproducible, versioned data lineage to regenerate the exact historical inputs for the affected period and confirm they're unchanged and correct — ruling the pipeline out as the cause before concluding the decline is real, economic alpha decay.
