A Feature Is Only As Honest As What It Actually Knew

The previous lesson in this pair, The Research Pipeline: Hypothesis to Honest Backtest, covered how to structure the process around a strategy idea — split the data honestly, cost it realistically, don't peek at the test set. This lesson goes one level deeper, into the features that pipeline actually feeds the model: the three specific, easy-to-miss ways a feature can quietly know things it shouldn't, and the discipline that keeps a result re-derivable months later instead of a one-time accident nobody can explain.

Section 1

A feature is anything a model is handed as an input

Not raw data itself — a deliberately computed quantity built from raw data, meant to help a model predict something it hasn't seen yet.

▢

Derived, not raw

A closing price is raw data. A 20-day rolling volatility, a distance-to-support in ATRs, a cointegration spread's z-score — those are features: computed from raw data, on purpose, to expose a pattern.

→

What the model actually sees

A model never sees "the market" — it sees a row of numbers, one per feature, at one point in time. If a number in that row is wrong about what was knowable then, the model is being trained on a fiction.

M

This repo already builds plenty

An ATR-based volatility z-score, a cointegration spread z-score sized beta-neutral, a payrolls revision-surprise score — real features already living in this codebase, all built the same way: raw series in, one computed number out.

⏱

Dated, whether or not it says so

Every feature value belongs to a specific point in time — the moment a live system would have had to compute it to actually use it for a real prediction that morning.

The previous lesson's leaks live at the validation stage — a train/test split that lets the future touch the past. This lesson's leaks live one stage earlier, inside a single feature's own construction, before any split even exists. A perfect split downstream cannot fix a feature that was already contaminated on the way in.
Section 2

Data leakage, in one sentence

A feature accidentally contains information that would not really have been available at the moment a live prediction had to be made.

Backtest Sharpe 2.4
≠
Live Sharpe ≈ 0.3
Same strategy, same rules — the backtest was quietly grading itself on a version of history the live system never actually had access to.

This is the single most common reason a backtest looks dramatically better than the same strategy performs live. Nothing about the model or the validation split has to be wrong — the leak lives earlier, in what a "feature" was secretly allowed to know at the moment it was computed. Because the leaked information genuinely happened, it correlates with the outcome almost perfectly; that's exactly what makes it so easy to miss and so damaging once it's gone unnoticed into production.

Why this is worth its own lesson

A backtest can pass every check the previous lesson describes — a genuinely out-of-sample split, realistic costs, no peeking at the test set — and still be worthless, if the features feeding it were never point-in-time honest to begin with. The split protects against one failure mode; this lesson covers a different one that happens earlier.

Section 3

Three specific ways it sneaks in

Same underlying mistake — using data from the wrong time — wearing three different disguises.

Try it
Full day's high/low
→
predicts 9am move
Using a value that wasn't actually known yet. A day's complete high and low aren't final until the session closes — using them to predict something earlier that same day hands the model a value from its own future. A live system at 9am simply could not have this number.
mean(all 2,000 rows)
→
z-score for row 40
Normalizing with the whole dataset's statistics. Scaling a feature using the mean/std of every row — including thousands that come chronologically after row 40 — bakes future extremes and regime shifts into a value dated to a much earlier day.
today's realized range
→
predicts today's direction
The feature IS the outcome, restated. A feature derived from — or too tightly bound to — the very event being predicted isn't predicting it, it's describing it after the fact. It looks trivially "predictive" and won't hold up live, because live it can't exist before the outcome does.

All three collapse to the same test: could this exact number have existed, in real time, at the moment the feature is dated to? If the honest answer is "not really," it's a leak — regardless of which column it's stored in or how reasonable the code looks.

Section 4

Watch look-ahead bias happen, visually

A prediction has to be made at a specific moment. A leaky feature reaches backward across that moment to grab information from after it.

Timeline
The fix is never a formula — it's a discipline: build every feature as if it had to run live, at the exact moment it's dated to, using only what existed then. If the value the feature needs didn't exist yet, the feature doesn't exist yet either.

Section 7

Target leakage: the feature that already knows the answer

The subtlest of the three, because the feature and the label can sit in different columns and still be two names for the same already-happened event.

Leaky
  • Label: "did the close finish above the open today"
  • Feature: today's realized volatility, or today's high-low range — both only exist because today's close already happened
  • Looks almost perfectly predictive in a backtest
  • Live, the feature can't be computed before the label is already decided
Honest
  • Label: "did the close finish above the open today"
  • Feature: yesterday's realized volatility, or a rolling average of the last 20 days' ranges
  • Looks weaker in a backtest — because it's telling the truth about how hard this is
  • Live, this feature genuinely exists before the prediction has to be made
The practical test isn't which column the number sits in — it's whether the feature could have been meaningfully known before the outcome was substantially determined. "They happen together" is the tell. A quiz question that quietly hands you the final score as one of its inputs is still just asking "did the team that scored more points win."
Section 8

Two more slow leaks, worth knowing even if they're not the headline three

📈

A trending raw level is a disguised time index

Feed a model a currency's raw, persistently trending price level instead of a return or z-score, and it can "predict" beautifully in-sample — mostly by learning which half of the sample a row is in. That trick evaporates the moment the trend changes direction.

🪦

Survivorship bias — a leak in which rows exist, not what they contain

Building a universe from "instruments tradeable today" silently drops everything that got delisted, devalued, or defaulted along the way — exactly the historical cases a strategy most needs to be tested against.

Neither one is a single feature reaching across time the way the three headline patterns are — a non-stationary level is a modeling-assumption failure wearing a feature-importance costume, and survivorship bias is a leak in the dataset's row list rather than any one row's values. Both produce the exact same symptom as the other three: a backtest that looks calmer than a live system, operating in real time with no foreknowledge of the future, would actually have experienced.

Section 9

Reproducibility is a separate, equally practical problem

Proving a result wasn't leaked is the job of everything above. Proving it can be rebuilt months later, and get the same answer, is a different job entirely.

Version data, code, and parameters together

"Which data," "which code," and "which parameter values" have to be pinned down as one unit. Version control on the code alone doesn't help if the underlying dataset silently gets revised without a matching version bump — the same script, run again, quietly produces a different number with no record of why.

Fixed seeds + point-in-time snapshots

A fixed random seed makes any randomized step reproducible. But a feature computed "as of December" using today's fully-revised data is a different feature than the one a live system in December could have actually built — reproducibility needs the data exactly as it stood back then, not just the current, possibly-restated version.

The trap

"The data hasn't changed since I ran this" is rarely actually true for macro or fundamental series — silent revisions are the norm, not the exception. Without a point-in-time snapshot archive, a result computed "as of" a historical date can never be proven free of a later revision, and can never be honestly reproduced once the source series has been revised again.

Section 10

Does this repo actually practice any of this?

Checked against the actual source code, not just assumed from the surrounding discipline.

What the code shows

Better than a blank slate. Several modules already compute features the causal, only-past way: GlobalLiquidity/mathx.py's rolling_z() is explicitly documented as "causal rolling z-score… using only the past"; forge/residual.py's causal_zscore() standardizes a residual against a window ending at the prior bar specifically so "this cannot manufacture" a self-referential leak; RegimeV2/backtest_v3.py builds its ATR volatility z-score from a rolling window and states outright "all computed causally (no look-ahead)"; and js/laborMarketEngine.js goes a step further on reproducibility's data-vintage problem specifically — its revisionScore() fetches both the FRED payrolls series and BLS's original first-published vintage (fetchFredInitialRelease) and scores the gap between them, rather than only ever looking at the current, fully-revised numbers.

Where this still needs qualifying

This discipline is real, but it's scattered per-module, not centralized. There's no single point-in-time feature store tagging every value with both a calendar date and a true availability date, no explicit publication-date join layer, and no evidence found of a deliberately survivorship-inclusive instrument universe or a general point-in-time snapshot archive across the codebase. Seeded, deterministic random-walk controls do exist (scripts/gen_vumanchu_vectors.mjs, run_sigma_definition_ab.mjs, and siblings), which covers reproducibility for synthetic test data — but that's a narrower guarantee than versioning a live research result's data, code, and parameters together as the section above describes.

Section 11

The checklist that catches most of this

🕒

Two dates, not one

Track a data point's calendar date and its true availability/publication date separately — join on the latter, always.

📏

Only-past statistics

Any normalization, z-score, or rank must come from an expanding or rolling window of strictly prior data — recomputed fresh at every point in time.

🗂️

Include the delisted

A universe built without the failed and discontinued instruments has already excluded a strategy's own worst cases before the test even starts.

📦

Snapshot, don't just save

Keep the data vintage as it stood historically, plus the code commit and parameter file — pinned together, not tracked separately and hoped to still match.

Section 12

Check yourself

Nothing is scored beyond this device. The explanation is the useful part.

Question 1

What does "point-in-time computable" mean for a feature?

Point-in-time computability is about honesty regarding what was actually knowable then — not about update frequency or window length.
Question 2

A feature uses a full day's high and low to predict which way price would move that same morning. What kind of leak is this?

The day's complete high/low only becomes final at the close. Using it earlier in the same day hands the model a value from its own future.
Question 3

A z-score feature is computed once using the mean/std of the entire dataset, including rows far in the future. What's wrong with it?

This is future-computed-statistics contamination: a live system on any given historical day could never have known the full dataset's eventual mean and std.
Question 4

Which is the clearest example of target leakage?

The feature and the label both depend on the same already-happened event — the feature is restating the outcome, not preceding it.
Question 5

Why isn't "the data hasn't changed since I ran this" a safe assumption for reproducibility?

Silent revisions to macro/fundamental series are the norm — a result is only truly reproducible once data, code, and parameters are versioned together as one unit.
Section 13

What to carry forward

01

A feature is any computed input a model uses to predict something — and it only earns that role if it could have genuinely existed at the moment it's dated to.

02

Look-ahead bias: using a value that wasn't actually known yet, like a full day's high/low to predict something earlier that same day.

03

Future-computed statistics: normalizing with the whole dataset's mean/std instead of only data available up to that point — a narrower, easy-to-miss cousin of a split-boundary leak.

04

Target leakage: a feature derived from, or too tightly bound to, the very outcome being predicted — trivially "predictive" in a way that never survives contact with live data.

05

Reproducibility is a separate, practical discipline — fixed seeds, version-pinned data snapshots, and documented feature-computation code, or a "finding" quietly stops being reproducible.

06

This repo already practices real causal feature computation in several modules — genuine progress, not a hypothetical concern, though it's scattered rather than centralized as unified point-in-time infrastructure.

What this now lets you do

Look at any feature — in this repo or anywhere else — and ask the one question that actually matters: could this exact value have existed, in real time, at the moment it's dated to? Spot the three specific disguises leakage wears, and know the difference between "this backtest number is honest" and "this result can be rebuilt the same way again in six months."
