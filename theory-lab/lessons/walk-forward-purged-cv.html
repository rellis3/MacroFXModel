Walk-Forward & Purged Cross-Validation

A chronological train/test split looks rigorous — but if your features are built from overlapping rolling windows, the boundary itself can leak the future into the past. This is the formal theory behind this repo's own "no lookahead" rule.

CONCEPT — the theory behind this repo's own OOS discipline ~16 min read Prereqs: Multiple Testing & the Look-Elsewhere Effect
TL;DR
  • Random k-fold CV assumes rows are exchangeable; time series aren't — shuffling can put day \(i+1\) in training while day \(i\) is the test row, which is literal lookahead, plus serially-correlated neighbors let a model "cheat" across the fold boundary.
  • Walk-forward validation fixes this by only ever training on \(\{i : i < T_k\}\) and testing on \(\{i : T_k \le i < T_k+h\}\) — the same "no lookahead" discipline this project's own house rule already states as "σ/regime/score for window \(i\) use data \(< i\) only," applied to the whole train/evaluate cycle.
  • A clean chronological split alone still leaks: a training row just before the boundary can have a forward-looking label that reaches into the test window, and a training row just after the test period can have a rolling feature window that reaches back into it.
  • The worked example (\(n=1{,}000\), \(w=20\), \(H=5\), test = days 500–599) shows this concretely: days 495–499 are purged for a label leak, days 600–618 for a feature leak, and a further 10-day embargo (days 619–628) buffers residual serial correlation the mechanical purge formula doesn't capture — training only resumes at day 629.
  • This project's own split/metrics reporting does a single clean chronological split with no purge/embargo — an honest gap, not a bug, but a checkable refinement worth applying to strategies whose features (HV20, rolling z-scores/percentiles, day-type estimators) lean on multi-day rolling windows near the split date.
Section 01

Why this matters

Every lesson in the Applied Statistics & Validation track eventually runs into the same practical question: once you've built a rule, how do you honestly find out whether it works on data it hasn't seen? The instinctive, textbook answer — split the data into folds, hold some out, average performance across folds — is standard cross-validation, and it is one of the most reliable tools in general machine learning. It is also, in its default random-shuffle form, flatly wrong for time series, including every price series this repo trades. Not "slightly optimistic" wrong — mechanically broken, in a way that can make a strategy with zero real edge look statistically solid.

The reason is that standard k-fold CV assumes each row of data is exchangeable — that shuffling rows and testing on a random subset tells you something valid about "unseen" data. Price data violates that assumption in two compounding ways: (1) nearby time points are serially correlated — today's volatility, trend, and regime look a lot like yesterday's, so a randomly shuffled fold is never truly independent of the rest of the sample, and (2) most features used in this repo (and in quantitative finance generally) are built from rolling windows — HV20, a 20-day rolling z-score, a rolling percentile — so a single row's feature value is a function of many neighboring rows' raw data. Shuffle the rows and you shuffle a feature that was never independent of its neighbors in the first place. This lesson works through why that specific combination breaks naive validation, what walk-forward validation fixes about it, and why walk-forward alone still isn't the whole fix — the more subtle failure mode that purging and embargoing exist to close.

💡
Plain-English intuition

Grading a weather forecaster with tomorrow's newspaper already on the desk

Imagine testing a weather forecaster by handing them a stack of 365 daily forecast sheets in random order and asking them to fill each one in, with all 365 days' actual weather also sitting on the desk in a separate pile, freely browsable. Even if the forecaster never deliberately peeks at "today's" answer, they can see next Tuesday's actual sunny skies while filling in this Tuesday's forecast — and if this Tuesday and next Tuesday happen to be part of the same warm spell (which nearby days usually are), that adjacent information quietly makes this Tuesday's forecast look better than it would if the forecaster genuinely only knew what had already happened. Random k-fold cross-validation on time series does exactly this: it randomly assigns some days to the "test" pile and others to the "train" pile without regard to chronology, so a model can end up being fit, in part, on data that comes after the day it's being graded on. The forecaster was never dishonest — the setup itself handed them the answer key. Walk-forward validation is the fix: train only on days that have already happened, test only on days that haven't yet — mirroring how a live forecaster actually operates, one day at a time, never able to see next Tuesday while filling in this Tuesday's sheet.

Section 02

The math, step by step

Why random k-fold CV is wrong for time series

Standard \(k\)-fold cross-validation partitions a dataset of \(n\) rows into \(K\) roughly equal folds, assigned at random, trains on \(K-1\) folds and tests on the remaining one, and rotates until every fold has served as the test set once. This is a good procedure when rows are (approximately) i.i.d. — independent draws from the same distribution, with no systematic relationship between a row's position in the dataset and its value. Under that assumption, a randomly held-out fold really is a valid stand-in for "data the model hasn't seen," because nothing about which rows land in which fold carries information the model could exploit.

Time-ordered price data is not i.i.d. in the way that matters here. Let \(i\) index chronological time (day 1, day 2, …, day \(n\)). Two problems compound:

\[ \text{Random fold assignment can place row } i+1 \text{ in training while row } i \text{ is in test.} \]

That is literal lookahead: a model evaluated on day \(i\) was fit, in part, using day \(i{+}1\)'s data — a day that, at the moment day \(i\)'s forecast would have had to be made live, had not happened yet. This is precisely the violation this project's own checklist forbids in one sentence: "No lookahead. σ/regime/score for window \(i\) use data \(< i\) only." Random k-fold CV, applied naively to a time-ordered series, breaks that rule by construction — not as an edge case, but on every fold, for roughly half the boundary rows.

Second, even where a fold's rows are all chronologically "before" or "after" a given test row in the crude sense of not being literally future observations of the exact same target, nearby time points are serially correlated: today's volatility regime, trend state, and many engineered features resemble yesterday's far more than two i.i.d. draws would. A model can partly "solve" a test fold not by learning a genuine, generalizable pattern, but by exploiting the fact that a training row from three days after (or before) the test row sits in a highly similar volatility/regime state — information a live forecaster, moving strictly forward through time, would never have had access to when the two rows are on opposite sides of the fold boundary. Randomly shuffling breaks the one property — chronological order — that made the data safe to cross-validate in the first place.

🧒 Explain like I'm 5

Normal cross-validation is like shuffling a deck of index cards before splitting them into piles — that's fine when each card is totally unrelated to its neighbors. But daily market data is more like a flip-book, where each page is almost a copy of the page before it. Shuffle a flip-book and hand someone random pages to "test" on while training on the rest, and they'll often be tested on a page that looks almost identical to one they already studied — not because they're smart, but because you shuffled something that was never really independent to begin with.

Walk-forward validation: train on the past, test on the strict future

The fix replaces random fold assignment with chronological fold assignment. Define a sequence of fold boundaries \(T_1 < T_2 < \dots < T_K\) and, for each fold \(k\), split strictly by time:

\[ \text{Train}_k = \{\, i : i < T_k \,\}, \qquad \text{Test}_k = \{\, i : T_k \le i < T_k + h \,\} \]
Train_kevery index strictly before the boundary \(T_k\)
Test_kthe strict future — indices from \(T_k\) up to \(T_k+h\)

Fit the model (or compute the score/selector) using only \(\text{Train}_k\), evaluate it only on \(\text{Test}_k\), then roll the boundary forward — \(T_{k+1} = T_k + h\) for a rolling fixed-length window, or simply extend the training set to include \(\text{Test}_k\) once it has been used, for an expanding window (the more common choice, and the one drawn in the diagram above) — and repeat for as many folds as the data allows. This is the exact discipline this project's own house rule already states: every σ, regime read, or score used for window \(i\) must be built only from data strictly earlier than \(i\). Walk-forward validation is that rule applied not just within a single feature calculation, but to the entire train/evaluate cycle — the model itself never has access to a boundary it hasn't crossed yet.

🧒 Explain like I'm 5

Walk-forward validation is simply testing a model the same honest way a real weather forecaster works: learn from everything up through today, make a call about tomorrow, then once tomorrow actually happens, add it to what you know and make a call about the next day. You never get to peek ahead — the training set only ever grows into days that have already occurred by the time you're being graded on them.

\(n\)total number of chronologically ordered observations (e.g. daily bars).
\(K\)number of walk-forward folds.
\(T_k\)the train/test boundary for fold \(k\) — the first index belonging to that fold's test set.
\(h\)the length of the test window for a given fold.
\(w\)the length of a rolling feature window (e.g. \(w=20\) for a 20-day rolling volatility, HV20).
\(H\)the forward label horizon — how many periods ahead the training target/outcome is computed over (e.g. a 5-day forward return used to label a trade a win or a loss).
\(e\)the embargo length — the extra buffer immediately after a test window during which no observation re-enters training.
\(\text{Train}_k, \text{Test}_k\)the training and test index sets for fold \(k\), after applying the chronological split (and, below, the purge/embargo corrections).

The subtler problem: overlapping feature windows leak across the boundary

A clean chronological split fixes the lookahead problem above — but it does not, on its own, fix a second, easier-to-miss leak. Almost every feature this repo (and quantitative finance generally) uses is not a single day's raw price — it's a function of a rolling window of nearby days: HV20 (20-day rolling volatility), a rolling z-score, a rolling percentile, an EWMA. Write the feature computed at index \(i\) as depending on the backward window

\[ \text{Feature}(i) = f\big(\text{bars}[\,i-w+1,\; i\,]\big) \]
[i−w+1, i]the backward-looking window a feature is built from

and, symmetrically, write a forward-looking training label — the outcome the model is actually being fit to predict, such as "did a trade opened at \(i\) win over the next \(H\) periods" — as depending on a forward window:

\[ \text{Label}(i) = g\big(\text{bars}[\,i,\; i+H\,]\big) \]
[i, i+H]the forward-looking window a training label is built from

Now look at what happens right at a chronological boundary \(T_k\). A training row \(i\) that is, by the letter of the rule, "strictly before" the test set (\(i < T_k\)) can still have a label that reaches forward into the test period whenever \(i + H \ge T_k\) — i.e. whenever \(i \ge T_k - H\). Its target value was computed, in part, from price action that occurs inside the test window. The training set never touched a test-period row directly, and the split date is technically respected — but the model was still fit using information that, in a live setting, would not have existed yet. Mirror the same logic on the other side of the boundary: a row \(i\) chronologically after the test period (relevant to a later fold, once \(\text{Test}_k\) has been absorbed back into training) can have a feature window that reaches backward into the just-tested-on period whenever \(i - w + 1 < T_k + h\), i.e. \(i < T_k + h + w - 1\). Both directions are the same failure: a window that straddles the boundary carries test-period information into a training row, even though every individual index respects "\(<\)" or "\(\ge\)" the split date on paper.

The trap: a clean chronological split date is necessary but not sufficient. The split date can be perfectly respected on paper while the feature/label windows straddling it still leak test-period information into training — the leak lives in the window, not the index.
🧒 Explain like I'm 5

Imagine a "no peeking" rule for a quiz where you're only forbidden from opening tomorrow's newspaper — but your study notes from yesterday happen to already summarize what's in it, because you wrote them using a several-day average that quietly reaches into tomorrow. You never touched the newspaper directly, so the rule looks respected, but the answer leaked in anyway through the notes. A rolling feature or a forward-looking label works the same way — it can smuggle test-period information across a perfectly clean-looking date.

Purging: removing the contaminated training rows

Purging (the term and the formal treatment are Marcos López de Prado's, in Advances in Financial Machine Learning) removes exactly the training rows identified above: any index \(i\) whose combined feature-and-label window overlaps the test interval is dropped from the training set entirely, in both directions:

\[ \text{Purge}_k = \Big\{\, i \in \text{Train}_k \;:\; \big[\,i-w+1,\; i+H\,\big] \,\cap\, \big[\,T_k,\; T_k+h\,\big) \ne \varnothing \,\Big\} \]

and the actually-usable training set for fold \(k\) is \(\text{Train}_k \setminus \text{Purge}_k\). This is a mechanical, checkable criterion — for a given \(w\), \(H\), and boundary, you can compute exactly which row indices must be dropped, rather than relying on "the split date looks clean."

🧒 Explain like I'm 5

Purging is just going back and physically throwing out any training flashcard whose notes reach into the material you're about to be quizzed on — even if the flashcard's own date says it belongs in the "study" pile. You can compute exactly which flashcards those are, ahead of time, from how far back or forward their notes reach, so there's no guessing about which ones to pull.

Embargo: a buffer for residual serial correlation

Purging removes every row with an explicit, window-length-computable overlap. But real financial series carry serial correlation that runs beyond the exact length of any one feature window or label horizon — volatility clustering, regime persistence, slow-moving order-flow effects that a hard cutoff at \(w\) or \(H\) days doesn't fully capture. Embargoing adds a further, deliberately conservative buffer of length \(e\) immediately after the test window, during which no row — even one whose mechanical window no longer technically overlaps — is allowed back into training:

\[ \text{Embargo}_k = \big[\, T_k + h,\; T_k + h + e \,\big) \]
eembargo length — a deliberate, conservative buffer
Embargo_kthe extra window held back after test, beyond the mechanical purge

Training on the next fold only resumes strictly after this embargo period ends. López de Prado's own guidance sizes \(e\) as a small fraction of the total sample (on the order of 1% of \(n\)) or ties it to the label horizon \(H\) directly; the exact size is a judgment call, but the principle is not — it is an explicit acknowledgment that the mechanical purge formula above is a lower bound on how much needs to be removed, not a provably complete one, given that real return series are correlated in ways a fixed window length only approximately describes.

🧒 Explain like I'm 5

Embargo is an extra "just to be safe" waiting period after the purge, the same way you might wait a bit longer than the recipe says before eating something out of the oven — the timer told you it should be done, but ovens don't behave with perfect precision, and a little extra margin costs almost nothing while protecting against the case where the timer alone wasn't quite enough.

🧮
Worked example

Counting the exact rows a purge/embargo scheme removes

Take a dataset of \(n=1{,}000\) daily bars, a 20-day rolling volatility feature (\(w=20\)), and a 5-day forward label horizon (\(H=5\)) — a trade opened on day \(i\) is labeled a win or a loss using the realized path over days \(i\) through \(i+5\). Set a fold boundary at day \(T=500\), with a 100-day test window (\(h=100\), so the test set is days 500–599).

Backward purge (label leak). A training day \(i < 500\) has a contaminated label whenever \(i + 5 \ge 500\), i.e. \(i \ge 495\). That purges training days 495–499 — 5 rows — because each of their labels was computed using price action on day 500 or later, which is inside the test window. A "clean-looking" split at day 500 quietly let 5 training labels see into the test set.

Forward purge (feature leak). Once fold 1's test period ends at day 599, the next fold would like to train on day 600 onward. But day 600's HV20 feature uses days 581–600 — 581–599 of which are inside the just-finished test window. The feature window stops overlapping test only once \(i - 19 > 599\), i.e. \(i \ge 619\). So days 600–618 — 19 rows — must also be purged before they're allowed back into training.

Embargo on top. Purging alone would let training resume at day 619. A conservative scheme adds an embargo of, say, \(e=10\) days beyond that mechanical cutoff — days 619–628 — as a buffer against serial correlation the window-length formula doesn't explicitly model. Training on the next fold only resumes at day 629, not day 600 and not day 619. Out of the roughly 129 days between the test set's start and where training safely resumes (500 through 628), 24 of them (5 backward-purged + 19 forward-purged) are removed by a mechanical, computable rule, and a further 10 are removed by a deliberate safety margin — none of this is visible if you only look at the split date itself.

🎯
A real-world trading scenario

The backtest that "looked" out-of-sample but wasn't

A researcher builds a strategy around a 20-day rolling-volatility feature (HV20) and validates it with what looks like a textbook-rigorous chronological train/test split at day 500: train on days 1–499, test on days 500 onward. No random shuffling, no obvious lookahead — the split date is respected everywhere, and the researcher reports a solid out-of-sample Sharpe ratio.

Here's the leak that split doesn't catch. Day 500's test-period volatility feature is computed from days 481–500 (the 20-day window ending on day 500). That's expected and fine on its own — a live model computing a feature for day 500 is entitled to use everything up through day 500. The problem is on the training side of the boundary: if the strategy's training labels are built from a forward-looking horizon (say, "did this trade win over the next 5 days"), then training days 495 through 499 — all comfortably inside the "train" bucket by date — have labels that were computed using price action on day 500 and just after. Those training rows' targets were quietly built, in part, from the exact same price moves that determine whether the model's day-500 test call was a winner. The model, during fitting, effectively got a preview of how that stretch of the market behaved before it was ever asked to "forecast" it.

Without purging those five training rows (and, symmetrically, embargoing the days right after the test period before the next fold's training resumes), the reported out-of-sample Sharpe ratio is quietly inflated by information that, relative to what a model making decisions live would have had, technically came from the future. The split date on the calendar was honest; the windows straddling it were not. This is exactly the gap a clean chronological split can hide and a purge/embargo scheme is built to close.

Section 03

How practitioners actually use this

Two overlapping traditions converge on the same discipline from different directions:

Algorithmic trading — "walk-forward optimization"

Robert Pardo's treatment (The Evaluation and Optimization of Trading Strategies) popularized rolling the train/test boundary forward repeatedly across a price history and comparing in-sample performance to out-of-sample performance on each roll. A commonly cited diagnostic is the walk-forward efficiency — roughly, OOS performance divided by IS performance on the same fold — with a ratio well below 1 flagging a parameter set that was overfit to its training window rather than genuinely robust. This tradition emphasizes rolling repeatedly (many folds, not one lucky split) over any one fold's result in isolation, for the same reason the multiple-testing lesson warns against trusting a single best-of-many slice: one good fold out of several is a weaker claim than a rule that holds up fold after fold.

ML-in-finance — "purged k-fold CV"

López de Prado's treatment formalizes the purge/embargo mechanics above as a drop-in replacement for scikit-learn-style k-fold CV specifically for finance, where cross-sectional ML models (not just single-series backtests) are common and the temptation to reach for standard, off-the-shelf k-fold tooling is strongest. His point is that the mechanical fix (purge the overlap, embargo a further buffer) is what lets you keep the statistical efficiency benefits of k-fold-style validation — using more of the data, running more folds — without reintroducing the lookahead that made random k-fold wrong for time series in the first place.

In practice, both traditions agree on the same checklist:

🚫

Never shuffle

Never assign folds at random for time-ordered data.

📏

Know the windows

Know the window length of every feature and label your model touches.

🧮

Compute, don't eyeball

Compute exactly which rows near a boundary need to be purged.

🛡️

Embargo on top

Add an embargo buffer rather than trusting the mechanical purge formula to be perfectly complete.

🔁

Judge across many folds

Judge a rule by its behavior across many rolled folds, not by one favorable-looking split.

⚠️
Common pitfalls

Ways this goes wrong in practice

  • Using scikit-learn's default KFold (or any shuffled split) on time-ordered data. The default shuffles rows before splitting unless you explicitly disable it — quietly reintroducing the exact lookahead this lesson opens with, even when the researcher believes they're doing "cross-validation" correctly because the tool is standard and well-tested elsewhere.
  • Trusting a single chronological split because "the date is respected." As the trading scenario above shows, respecting the split date is necessary but not sufficient. The leak lives in the feature/label windows, not in whether an index number is technically greater or less than the split date.
  • Sizing the purge window using only the feature length, forgetting the label horizon. Purging is a two-directional problem — a backward-leaking label horizon \(H\) and a forward-leaking feature window \(w\) are different quantities that both need to be accounted for; purging only one direction still leaves a leak on the other side of the boundary.
  • Treating embargo as optional "extra caution" rather than a distinct failure mode it solves. Purging handles the leak you can compute exactly; embargo handles the leak you can't fully compute, from serial correlation beyond the window length. Skipping embargo because "the purge formula already handles it" conflates the two.
  • Reporting walk-forward results from only one or two rolled folds. A rule that happens to look good on one particular boundary date is subject to the same "best of many looks" problem as any other single result — Pardo's walk-forward-efficiency tradition specifically wants many rolled folds, not one favorable split, for the same reason the multiple testing lesson distrusts a single winning slice.
  • Forgetting purging/embargo is about validation, not a source of edge. A correctly purged and embargoed OOS test can still show a null result — the discipline only makes the OOS number honest, it doesn't manufacture a positive one. A strategy that fails a properly purged test failed for a real reason, not because the validation was "too strict."

Key Takeaways

✓Random k-fold CV is mechanically broken for time series. Shuffling can put day \(i+1\) in training while day \(i\) is the test row — literal lookahead, not a subtle statistical nuance.
✓Walk-forward validation trains strictly on the past. \(\text{Train}_k=\{i:i < T_k\}\), \(\text{Test}_k=\{i:T_k\le i < T_k+h\}\) — the same "no lookahead" rule this project's own house rule states, applied to the whole train/evaluate cycle.
✓A clean split date alone still leaks. Rolling feature/label windows straddling the boundary can carry test-period information into training even when every index technically respects the split.
✓Purging removes the mechanically computable overlap. Any training row whose combined feature+label window touches the test interval is dropped — exact, checkable, not eyeballed.
✓Embargo buffers what purging can't formula-ize. Real serial correlation runs beyond any window length — embargo is a deliberate, conservative extra margin on top of the mechanical purge.
⚠This project's own split/metrics reporting has no purge/embargo yet. An honest gap, not a bug — a checkable refinement worth applying to strategies whose features lean on multi-day rolling windows near the split date.
⚠Passing a purged test is not proof of edge. It only makes the OOS number honest — it says nothing about costs, economic mechanism, or whether the result clears the multiple-testing chance baseline.
Section 05

Self-test

Q1. Why is random k-fold cross-validation wrong for time series even if you never literally look at a "future" row directly?
Two separate problems compound. First, random fold assignment can place a chronologically later row (day \(i+1\)) into the training set while an earlier row (day \(i\)) sits in the test set — which is literal lookahead: the model evaluated on day \(i\) was fit partly using data from a day that, in a live setting, hadn't happened yet. Second, even rows that don't literally violate ordering are still serially correlated with their neighbors (volatility clustering, regime persistence), so a model can exploit similarity to nearby rows across the fold boundary rather than learning a pattern that would have generalized to genuinely unseen future data. Standard CV assumes rows are exchangeable draws with no such structure; time-ordered financial data violates that assumption by construction, not as an edge case.
Q2. How does walk-forward validation directly implement the "no lookahead" rule this project follows?
Walk-forward validation defines each fold's train set as strictly \(\{i : i < T_k\}\) and test set as strictly \(\{i : T_k \le i < T_k + h\}\), so by construction no training observation is ever chronologically later than any test observation in the same fold. That is exactly the rule "σ/regime/score for window \(i\) use data \(< i\) only," applied not just inside a single feature calculation but to the entire train/evaluate cycle: the model is never fit using information from a time index it hasn't reached yet.
Q3. What specific problem does "purging" solve that a plain chronological split doesn't?
A plain chronological split only guarantees that a row's own time index respects the train/test boundary — it says nothing about the window a feature or label at that index was computed from. A training row can sit strictly before the test boundary by index, yet have a forward-looking label (e.g. a 5-day-ahead outcome) that was computed using price action that falls inside the test period, or a training row just after the test period can have a backward-looking feature (e.g. a 20-day rolling volatility) that reaches back into the test period. Purging removes exactly those rows — any training index whose combined feature-and-label window overlaps the test interval — closing a leak that the split date alone leaves open.
Q4. In the worked example (n=1,000, w=20, H=5, test = days 500–599), why are training days 495–499 purged, and why are days 600–618 purged separately from the embargo?
Days 495–499 are purged because their forward-looking labels use a 5-day horizon (\(H=5\)), so a label computed at day \(i\) uses data through day \(i+5\); for \(i \ge 495\), \(i+5 \ge 500\), meaning the label reaches into the test period that starts at day 500 — a backward (label) leak. Days 600–618 are a separate, forward (feature) leak: day \(i\)'s 20-day HV20 window is \([i-19, i]\), which still overlaps the test period (ending day 599) for any \(i\) up to 618 (\(i-19 \le 599\)). Both are mechanical, purge-formula-computable overlaps. The embargo (days 619–628 in the example) is a separate, additional buffer added on top of that mechanical cutoff — it isn't required by the window-overlap formula at all, it's a deliberate safety margin against serial correlation the formula doesn't explicitly capture.
Q5. In the trading scenario (20-day vol feature, split at day 500), what exactly leaks, and in which direction — from test into train, or train into test?
It leaks from the test period backward into training, via the training labels. Day 500's own test feature (built from days 481–500) isn't the problem — a live model is entitled to use everything through the day it's forecasting. The leak is that training days 495–499, which sit on the "train" side of the split date, have forward-looking labels that were computed using price action on day 500 and after — i.e., inside the test window. The model was fit, in part, using information about how the test period actually played out, even though every index technically respected the chronological split.
Q6. Does passing a correctly purged and embargoed walk-forward test prove a strategy has real edge?
No. Purging and embargoing only remove a specific source of contamination from the validation procedure — they make the resulting OOS number honest relative to what a live, strictly forward-moving process would have seen. They say nothing about whether the underlying idea has a plausible economic mechanism, whether the effect survives realistic costs, whether it holds up across many rolled folds rather than one, or whether it clears the multiple-testing chance baseline if many variants were tried. A properly validated null result is still a null result; purging and embargo are necessary correctness conditions for the test, not evidence of edge on their own.

  • Marcos López de Prado, "The 10 Reasons Most Machine Learning Funds Fail," Journal of Portfolio Management (2018) — a practitioner-facing summary that includes leakage from non-purged cross-validation among the recurring, avoidable failure modes.
  • Campbell R. Harvey & Yan Liu, "Backtesting," Journal of Portfolio Management (2015) — broader context on why walk-forward and out-of-sample discipline specifically (not just in-sample fit quality) is what separates a real backtest from a curve-fitting exercise.
