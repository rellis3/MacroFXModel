Section 2

Storage has to match the access pattern

Historical tick/bar data is almost always queried as "give me a date range of these few columns," not "give me one full row."

Row-oriented storage
  • Reads an entire record — every column — to get at just one or two of them
  • A poor structural match for column-range queries over long histories
  • Mixed row data (price, volume, timestamp, metadata) compresses poorly together
Columnar storage (Parquet-style)
  • Each column's values stored contiguously — a query reads only what it needs
  • Similar neighboring values compress far better than mixed rows
  • Supports schema evolution — new columns can be added without breaking old readers

None of this makes columnar storage universally "correct" — a system appending single ticks continuously and reading them back immediately has different needs. But for storing and repeatedly querying large historical archives, columnar formats are the practitioner default for concrete structural reasons, not fashion.

Section 3

One authoritative pipeline, or two that quietly drift

"Single source of truth" sounds obvious stated abstractly. It's still one of the most common real failures in data engineering.

Two independent recomputations
  • Research team and risk team each build their own "adjusted close" from the same raw feed
  • Both match closely at first — the corrections are small, memory is fresh
  • A rounding tweak here, an edge-case fix there, each reasonable in isolation
  • Two years later the numbers don't reconcile, and nobody can say exactly why
One authoritative pipeline
  • Exactly one system computes each derived series
  • Every downstream consumer reads its output — nobody recomputes it independently
  • Changes are reviewed once, in one place, against one shared history
  • There is only ever one number to reconcile against
The trap

"Our two systems compute this the same way" is almost never re-verified after the initial build — it's assumed true because it was true on day one. Neither copy is necessarily wrong in isolation. The failure is that there were ever two copies of the same authoritative computation running at all.

Section 4

Lineage tells you where a value came from. Versioning tells you when its meaning changed.

Data lineage / audit trails

The ability to answer, for any value sitting in the store today, exactly which raw inputs and which version of the code produced it — specifically enough to regenerate it from scratch. Without it, a suspicious value months later has no reconstructable history.

Schema versioning

An explicit tag marking when a column's shape, name, or units change. Without it, a downstream reader keeps interpreting new data as if it still meant the old thing — not an error, just a silent misread.

Worked example — a silent unit change
1.8 (bp)
same column, no version tag →
0.00018 (fraction)
A cost model built for basis points now reads the new number as roughly 10,000× tighter than intended. The backtest doesn't error — it just quietly becomes dramatically optimistic about transaction costs from that date forward.
A version tag on the column — or a rename to spread_frac alongside the old spread_bp — turns this into a visible, catchable break instead of an invisible one.

Section 6

Why the curve alone can never settle it

Each of the earlier lessons in this category is a place a silent break can hide, producing the exact same visible symptom.

1

A bar-construction method changed

Switching from time bars to a different construction upstream (Lesson 1) shifts every downstream feature slightly — no error, just different numbers.

2

A cleaning threshold drifted

An outlier filter (Lesson 2) tightened or loosened without anyone noticing changes which ticks survive into every backtest from that point on.

3

An adjustment method shifted

A corporate-action or roll adjustment (Lesson 3) computed slightly differently puts a small, compounding error into every adjusted price after it.

4

A feature started leaking differently

A point-in-time boundary (Lesson 4) that used to be respected — or a feature that used to leak and got fixed — changes what the model was effectively trained to see.

Both a genuine, honest decay and any one of these silent breaks produce the same visible signature: performance that gradually gets worse, with no single dramatic break to point to. The equity curve carries zero information distinguishing "the market changed" from "the data quietly became wrong." Something else has to carry that information instead.

Section 10

Check yourself

Nothing is scored beyond this device. The explanation is the useful part.

Question 1

Why is columnar storage the better structural fit for large historical tick/bar archives?

Tick/bar data is queried as "a date range of a few columns" far more often than "one full row." Columnar layouts keep each column contiguous, so a query skips everything it doesn't need — and similar neighboring values compress better than mixed rows.
Question 2

Two teams independently recompute "adjusted close" from the same raw feed, both starting from correct logic. What happens?

Small, individually reasonable changes — a rounding tweak, an edge-case fix — applied to one copy and not the other accumulate into real divergence. The failure is structural: there were ever two independently maintained copies at all.
Question 3

A "spread" column silently changes from basis points to a decimal fraction, with no version tag. What happens downstream?

The column's name and shape stayed the same, so nothing signals the unit changed. A model built for basis points keeps reading the new numbers as if they meant the old thing — silently, with no error.
Question 4

A live strategy's performance is declining. Can you tell genuine alpha decay from a pipeline bug using the equity curve alone?

Both causes look identical on an equity curve: a gradual worsening with no single dramatic break. Only reproducible, versioned data lineage lets you re-run the same strategy against different data vintages and isolate which one actually changed.
Section 11

What to carry forward

01

Columnar storage (Parquet-style) is the practitioner standard for historical tick/bar archives — fast column-range reads, better compression, schema evolution support.

02

Let exactly one authoritative pipeline compute each derived series. Independent recomputation drifts apart over time, even when both sides start out correct.

03

Data lineage means being able to regenerate any historical value from its exact raw inputs and exact code version — without it, a suspicious value has no reconstructable history.

04

An unversioned schema change — a renamed column, a changed unit — breaks downstream consumers silently, not with an error.

05

A genuine strategy decay and a silent pipeline bug produce the identical signature on an equity curve — gradual decline, no single dramatic break.

06

The fix is a diagnostic re-run: hold the strategy fixed and swap data vintages to isolate whether the degradation traveled with the data or with the market.

What this now lets you do

Re-run any live strategy against a frozen, versioned data snapshot from any earlier point, and check whether a new performance decline traveled with a data or pipeline change — or is a genuine market shift. That turns "is my edge dying?" from a guess into a testable question, and closes the arc this category has been building: from raw ingestion, through cleaning and adjustment and point-in-time serving, to durable, versioned storage that keeps every earlier stage's output honest months and years later.
