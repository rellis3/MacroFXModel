Data Architecture, Storage & Versioning

This closes out the category. Lessons 1–4 built a pipeline — ingest raw ticks, clean them, adjust for corporate actions, serve them point-in-time — and each one produces a value that has to live somewhere and be trusted later. This lesson is that layer underneath: how the data gets stored, why two "identical" pipelines quietly drift apart, and why a live strategy's performance can degrade for two completely different reasons that look, on the equity curve, exactly the same.

The whole idea
🎧 Listen · the four-minute version

A trader and a quant talk the lesson through. No symbols, just the idea and one worked number, so it works on a walk or a commute.

Data architecture sounds like plumbing. Why should a trader care?

Because when the plumbing leaks, it looks exactly like your edge dying. A slow pipeline bug and real alpha decay draw the same equity curve.

How does a pipeline go bad without anyone noticing?

The commonest way is two copies of the same sum. Say research and risk each build their own adjusted close from the same raw feed. On day one they match.

And then?

Research fixes how it handles a rare zero-volume day. Risk changes how it rounds a dividend factor. Each change is sensible. Two years later the numbers disagree, and nobody can say why.

So keep one copy.

One authoritative pipeline that everyone reads. And a record of which raw inputs and which code version made every value, so you can rebuild it months later.

What's the other trap?

A field that changes meaning without a label. A spread column has always been in basis points. A typical reading is one point eight. Someone switches it to a decimal fraction, so the same spread is now zero point zero zero zero one eight.

And the cost model still thinks it's basis points.

So it understates every cost by a factor of ten thousand. No error, no crash. The backtest just turns quietly optimistic from that day on.

Has that kind of thing ever blown up for real?

Knight Capital, the first of August twenty twelve. Their order router ran on eight servers. New code reached seven. The eighth kept the old code.

And that mattered because?

The new code reused a flag. On seven servers it meant a new kind of retail order. On the eighth it still meant run an old function called Power Peg, which could no longer see its fills. So it kept sending orders.

How bad?

About four hundred and forty million dollars in roughly forty-five minutes. And when they rolled back the new code, all eight servers started behaving like the stale one.

So the one-line version?

One source for every number, a version on every stage and every field, and when performance slips, rule out the plumbing before you blame the market.

Section 2

Storage has to match the access pattern

Historical tick/bar data is almost always queried as "give me a date range of these few columns," not "give me one full row."

Row-oriented storage
  • Reads an entire record — every column — to get at just one or two of them
  • A poor structural match for column-range queries over long histories
  • Mixed row data (price, volume, timestamp, metadata) compresses poorly together
Columnar storage (Parquet-style)
  • Each column's values stored contiguously — a query reads only what it needs
  • Similar neighboring values compress far better than mixed rows
  • Supports schema evolution — new columns can be added without breaking old readers

None of this makes columnar storage universally "correct" — a system appending single ticks continuously and reading them back immediately has different needs. But for storing and repeatedly querying large historical archives, columnar formats are the practitioner default for concrete structural reasons, not fashion.

Section 3

One authoritative pipeline, or two that quietly drift

"Single source of truth" sounds obvious stated abstractly. It's still one of the most common real failures in data engineering.

Two independent recomputations
  • Research team and risk team each build their own "adjusted close" from the same raw feed
  • Both match closely at first — the corrections are small, memory is fresh
  • A rounding tweak here, an edge-case fix there, each reasonable in isolation
  • Two years later the numbers don't reconcile, and nobody can say exactly why
One authoritative pipeline
  • Exactly one system computes each derived series
  • Every downstream consumer reads its output — nobody recomputes it independently
  • Changes are reviewed once, in one place, against one shared history
  • There is only ever one number to reconcile against
The trap

"Our two systems compute this the same way" is almost never re-verified after the initial build — it's assumed true because it was true on day one. Neither copy is necessarily wrong in isolation. The failure is that there were ever two copies of the same authoritative computation running at all.

Section 4

Lineage tells you where a value came from. Versioning tells you when its meaning changed.

Data lineage / audit trails

The ability to answer, for any value sitting in the store today, exactly which raw inputs and which version of the code produced it — specifically enough to regenerate it from scratch. Without it, a suspicious value months later has no reconstructable history.

Schema versioning

An explicit tag marking when a column's shape, name, or units change. Without it, a downstream reader keeps interpreting new data as if it still meant the old thing — not an error, just a silent misread.

Worked example — a silent unit change

A cost model built for basis points now reads the new number as roughly 10,000× tighter than intended. The backtest doesn't error — it just quietly becomes dramatically optimistic about transaction costs from that date forward.
A version tag on the column — or a rename to spread_frac alongside the old spread_bp — turns this into a visible, catchable break instead of an invisible one.
Section 5

A live strategy's performance is declining. Below are two completely different root causes — drawn from realistic numbers, not decorated to look alike.

Two equity curves
Same shape, same date, same magnitude of decline. In Case A, the market structure the strategy exploited genuinely weakened. In Case B, the market behavior never changed — a data-cleaning threshold, a leakage flip, or a bar-construction tweak quietly broke, and the strategy is reacting to corrupted input. Section 6

Why the curve alone can never settle it

Each of the earlier lessons in this category is a place a silent break can hide, producing the exact same visible symptom.

1

A bar-construction method changed

Switching from time bars to a different construction upstream (Lesson 1) shifts every downstream feature slightly — no error, just different numbers.

2

A cleaning threshold drifted

An outlier filter (Lesson 2) tightened or loosened without anyone noticing changes which ticks survive into every backtest from that point on.

3

An adjustment method shifted

A corporate-action or roll adjustment (Lesson 3) computed slightly differently puts a small, compounding error into every adjusted price after it.

4

A feature started leaking differently

A point-in-time boundary (Lesson 4) that used to be respected — or a feature that used to leak and got fixed — changes what the model was effectively trained to see.

Both a genuine, honest decay and any one of these silent breaks produce the same visible signature: performance that gradually gets worse, with no single dramatic break to point to. The equity curve carries zero information distinguishing "the market changed" from "the data quietly became wrong." Something else has to carry that information instead.

Section 10 · It actually happened

1 August 2012: Knight Capital's 45 minutes

It actually happened

Knight updated its order router for a new NYSE retail program. Per the SEC's order, the new code reached seven of eight servers. It reused a flag that once switched on "Power Peg", code dormant since 2003. On the eighth server the flag still ran Power Peg, which could no longer see fills, so it kept sending orders. Removing the new code from the other seven made it worse. In about 45 minutes: over 4 million executions in 154 stocks and a loss of about $440 million (the SEC later said more than $460 million).

Section 11

What this desk found, and where the textbook breaks

Desk data: base rate backtest-artifacts: a backtest that looks too good has a bug, usually in what it was allowed to see. The Fibonacci-level system: 85.7% backtest win rate vs 39.6% live. One mean-reversion system's entire edge: stops not live for the first hour. A volatility tool: 95% of "wins" scored before entry. Audit the machinery before calling it decay.
Where the textbook version breaks

Drift and silent schema changes are usually framed as slow research-data problems found by reconciliation. In a live router a meaning mismatch loses money every second. And rollback is only safe if the meaning of every flag is versioned with the code: Knight's revert spread the fault to all eight servers.

Section 12

Check yourself

Nothing is scored beyond this device. The explanation is the useful part.

Question 1

Why is columnar storage the better structural fit for large historical tick/bar archives?

Tick/bar data is queried as "a date range of a few columns" far more often than "one full row." Columnar layouts keep each column contiguous, so a query skips everything it doesn't need — and similar neighboring values compress better than mixed rows.
Question 2

Two teams independently recompute "adjusted close" from the same raw feed, both starting from correct logic. What happens?

Small, individually reasonable changes — a rounding tweak, an edge-case fix — applied to one copy and not the other accumulate into real divergence. The failure is structural: there were ever two independently maintained copies at all.
Question 3

A "spread" column silently changes from basis points to a decimal fraction, with no version tag. What happens downstream?

The column's name and shape stayed the same, so nothing signals the unit changed. A model built for basis points keeps reading the new numbers as if they meant the old thing — silently, with no error.
Question 4

A live strategy's performance is declining. Can you tell genuine alpha decay from a pipeline bug using the equity curve alone?

Both causes look identical on an equity curve: a gradual worsening with no single dramatic break. Only reproducible, versioned data lineage lets you re-run the same strategy against different data vintages and isolate which one actually changed.
Your call
Scenario drill · 1 August 2012

New router code, eight servers, and error emails before the open

You run a large US equity market maker's automated order router. The New York Stock Exchange's new Retail Liquidity Program starts today, and new router code has been deployed for it. The router runs on eight servers. The new code reuses an old flag that once switched on a retired function. Before the open, automated emails start arriving that flag errors. The bell is minutes away. What do you do?

  1. Open on schedule. The deployment was checked on the servers you looked at.
    "The servers you looked at" is the gap. A copy you did not verify is a second version of the truth, and a reused flag means whatever the code on that copy says it means.
  2. Hold the router back until every server is confirmed on the same code version and the reused flag means the same thing everywhere.
    This treats the error emails as a version check failing. One authoritative version, verified on every copy before it trades, is the single-source-of-truth rule applied at market speed. Missing the first minutes of a new program costs little next to an unbounded order loop.
  3. Open on schedule, and if anything misbehaves, roll every server back to the previous version.
    A rollback of code alone is only safe if the meaning of every flag rolls back with it. Here the old code would read the new flag as "run the retired function", so a rollback spreads the fault instead of removing it.
  4. Open on schedule but with tight order-rate and position limits on the router.
    Limits shrink the damage, which is worth a lot. But you would still be trading on a version mismatch you were warned about, and hoping the limits catch whatever it does.

What happened. Knight Capital opened on schedule. The new code had reached seven of eight servers; on the eighth, the reused flag still started the old Power Peg function, which could no longer track fills and kept sending orders. The error emails were not acted on. Staff then removed the new code from the seven good servers, which made all eight behave like the stale one. In about 45 minutes the router produced more than 4 million executions in 154 stocks. The loss was about $440 million by the firm's own estimate; the SEC's 2013 order put it at more than $460 million and fined Knight $12 million. Knight needed emergency outside capital within days and was later acquired.

Section 13

What to carry forward

01

Columnar storage (Parquet-style) is the practitioner standard for historical tick/bar archives — fast column-range reads, better compression, schema evolution support.

02

Let exactly one authoritative pipeline compute each derived series. Independent recomputation drifts apart over time, even when both sides start out correct.

03

Data lineage means being able to regenerate any historical value from its exact raw inputs and exact code version — without it, a suspicious value has no reconstructable history.

04

An unversioned schema change — a renamed column, a changed unit — breaks downstream consumers silently, not with an error.

05

A genuine strategy decay and a silent pipeline bug produce the identical signature on an equity curve — gradual decline, no single dramatic break.

06

The fix is a diagnostic re-run: hold the strategy fixed and swap data vintages to isolate whether the degradation traveled with the data or with the market.

07

A version mismatch can run at market speed: Knight Capital's eighth, un-updated server read a reused flag the old way and lost about $440 million in ~45 minutes. Desk context: backtest-to-live gaps (85.7% vs 39.6%) get the machinery audited before anyone says "decay".

What this now lets you do

Re-run any live strategy against a frozen, versioned data snapshot from any earlier point, and check whether a new performance decline traveled with a data or pipeline change — or is a genuine market shift. That turns "is my edge dying?" from a guess into a testable question, and closes the arc this category has been building: from raw ingestion, through cleaning and adjustment and point-in-time serving, to durable, versioned storage that keeps every earlier stage's output honest months and years later.
