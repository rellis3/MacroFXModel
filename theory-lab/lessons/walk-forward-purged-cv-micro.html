Lesson 24 · Applied Statistics & Validation

A Clean Split Date Isn't the Same as No Lookahead

Random k-fold cross-validation is a dependable workhorse for most machine learning — and it is flatly wrong for time series, including every price series this repo trades. This guide works through why shuffling breaks a sequence that was never independent to begin with, what walk-forward validation fixes about it, and why a clean chronological split still isn't the whole fix — the quieter leak that purging and embargoing exist to close.

Section 1

Shuffling assumes rows don't know each other

Standard k-fold cross-validation is a good, reliable procedure — for data where that assumption actually holds.

K

Random fold assignment

k-fold splits n rows into K folds at random, trains on K−1 of them, tests on the remaining one, and rotates until every fold has served as the test set once.

↔

Serial correlation

Today's volatility, trend, and regime look a lot like yesterday's. A randomly shuffled fold is never truly independent of the rest of the sample.

w

Rolling-window features

Most features here — HV20, a rolling z-score, a rolling percentile — are built from many neighboring rows, not one. Shuffle the rows and you shuffle a feature that was never independent of its neighbors.

→|

Literal lookahead

Random assignment can place day i+1 in training while day i sits in test. A model graded on day i was fit, in part, using a day that hadn't happened yet.

Why this matters here

This project's own checklist already states the rule for a single feature: "σ/regime/score for window i use data < i only." Random k-fold CV breaks that exact rule by construction — not as a rare edge case, but on roughly half the boundary rows of every fold.

Section 2

Watch the leak happen

The same ten days of data, split two different ways. Toggle between them.

Try it
Day 6 lands in training while day 5 — one day earlier — sits in test. Whatever day 6 contributed to the model, day 5's grade was never a clean "unseen data" test. Multiply this by every fold and roughly half the boundary rows carry the same problem.
Nothing crosses the boundary backward. Train uses everything strictly before T. Test uses only the strict future right after it. Days 9-10 simply wait their turn for a later fold.

This is the entire fix, before any formula: stop assigning folds at random, and assign them by time instead. Everything else in this lesson is about a second, easier-to-miss version of the same leak that survives even after you make this fix.

Section 3

Train on everything before the line, test on what comes right after

Define a boundary T_k for fold k, and split strictly by time on either side of it.

Train_k = { i : i < T_k }
→
Test_k = { i : T_k ≤ i < T_k+h }
Fit using only Train_k, grade only on Test_k, then roll the boundary forward — T_{k+1} = T_k + h — and repeat for as many folds as the data allows.
Rolling window

The training window has a fixed length and slides forward each fold — old data drops off the back as new data joins the front. Useful when older regimes are believed to stop being relevant.

Expanding window

Training simply grows to absorb each fold's test period once it has been used, never discarding history. The more common choice in practice, and the one this guide's diagrams use.

This is the exact discipline this project's own house rule already states for a single feature — "use data before i only" — applied to the entire train-and-evaluate cycle instead of just one calculation. The model never gets access to a boundary it hasn't crossed yet.

Section 4

A clean split date isn't sufficient

Almost every feature or label used here isn't built from one row — it's built from a window of rows around it. That window can straddle the boundary even when every row's own index respects it.

Feature window — looks backward

Feature(i) = f(bars[i−w+1, i]) — a 20-day rolling volatility, say. A training row just after the test period can still have a feature window reaching back into it, whenever i − w + 1 < T_k + h.

Label window — looks forward

Label(i) = g(bars[i, i+H]) — "did a trade opened at i win over the next H days." A training row just before the boundary can still have a label reaching forward into the test set, whenever i + H ≥ T_k.

The trap

A clean chronological split date is necessary but not sufficient. It can be respected perfectly on paper while the feature or label windows straddling it still carry test-period information into training — the leak lives in the window, not the index.

Section 5

Purging removes it exactly; embargo adds a margin

Two separate fixes for two separate failure modes.

✂

Purging

Any training row i whose combined feature-and-label window [i−w+1, i+H] overlaps the test interval [T_k, T_k+h) gets dropped. A mechanical, computable rule — not a judgment call.

⏳

Embargo

A further buffer of length e, immediately after the test window, during which no row re-enters training — even one whose window no longer technically overlaps. It exists because real serial correlation runs beyond any window length a formula fully captures.

The actually-usable training set for fold k is Train_k with the purge rows removed, and the next fold's training only resumes strictly after the embargo period ends. Purging closes the leak you can compute exactly; embargo covers the part you can't.

Section 6

Counting the exact days a purge/embargo scheme removes

n = 1,000 daily bars, a 20-day rolling volatility feature (w = 20), a 5-day forward label horizon (H = 5), a boundary at day T = 500 with a 100-day test window (h = 100, so test = days 500-599).

←

Backward purge (label leak) — 5 rows

Training days 495-499 are purged: their 5-day-forward labels use price action through day i+5, which reaches day 500 or later — inside the test window.

→

Forward purge (feature leak) — 19 rows

Training days 600-618 are purged: day i's 20-day HV20 window still reaches back into the test period, which only stops overlapping once i ≥ 619.

⏳

Embargo — a further 10 days

Days 619-628 are held back purely as a conservative buffer, on top of the mechanical cutoff. Training only resumes on day 629 — not day 600, and not day 619.

Out of the roughly 129 days between the test set's start and where training safely resumes, 24 of them are removed by a computable rule and a further 10 by a deliberate safety margin — none of it visible if you only look at the split date.

Section 8

Two traditions, one discipline

Two overlapping literatures converge on the same fix from different directions.

Trading — "walk-forward optimization"

Robert Pardo's treatment rolls the train/test boundary forward repeatedly and tracks walk-forward efficiency — roughly, OOS performance divided by IS performance on the same fold. A ratio well below 1 flags a parameter set overfit to its training window. The emphasis is on rolling many folds, not trusting any one favorable split.

ML-in-finance — "purged k-fold CV"

Marcos López de Prado's treatment formalizes the purge/embargo mechanics as a drop-in replacement for standard k-fold CV, specifically for finance — letting you keep k-fold's statistical efficiency (using more of the data, running more folds) without reintroducing the lookahead that made random k-fold wrong in the first place.

Both traditions land on the same checklist: never shuffle time-ordered data; know every feature and label window's length; compute — don't eyeball — which rows near a boundary must be purged; add an embargo rather than trust the purge formula's completeness; and judge a rule by its behavior across many rolled folds, not one good-looking split.
Section 9

Does this repo actually do this?

Checked against the actual validation scripts, not just what a comment claims.

What the code shows

Most of this repo's OOS scripts (oos_validate_exposure_cap.mjs, oos_validate_currency_loss_gate.mjs, and their siblings under scripts/) do exactly a single chronological split: trades on or before a cutoff date are "in-sample," everything after is "out-of-sample," and a parameter is chosen from the in-sample slice and frozen before the OOS side is ever touched. That's the plain chronological-split discipline this lesson opens with — and just like the trading scenario above, there's no purge gap and no embargo at the cutoff: the OOS set begins on the very next trade date.

There is one real exception worth flagging. scripts/walkforward_validate_exposure_cap.mjs — added in this same codebase as a direct follow-up — replaces the single split with genuine multi-fold walk-forward validation: four sequential blocks, each fold choosing its parameter from its own in-sample slice only and testing on a fresh, untouched out-of-sample block. That's exactly the "many rolled folds, not one lucky split" discipline from the previous slide, and it's real progress over a single static split.

Where this needs qualifying

Even that walk-forward script has no purge or embargo gap at any fold boundary — training stops exactly at the cutoff date and testing starts on the very next one. Some of the trade records it validates already trail rolling-window mechanics upstream (a chandelier stop trailing a rolling ATR, for one), so the boundary-window leak this lesson describes is a live, checkable question here, not a hypothetical one — a worthwhile next refinement, not evidence anything reported so far is wrong.

Section 10

Quick check

Nothing is scored beyond this device. The explanation is the useful part.

Question 1

In one sentence, why is random k-fold CV wrong for time series?

Random fold assignment can literally train on a future day while grading an earlier one, and even where it doesn't, serially correlated neighbors let a model "cheat" across the fold boundary.
Question 2

In walk-forward validation, how is Test_k defined?

Train_k is everything strictly before the boundary; Test_k is the strict future window of length h that starts right at it.
Question 3

A training row's label depends on prices up to H days ahead. Which rows need purging for a test boundary at T?

Those are exactly the training rows whose forward-looking label reaches into the test period, even though their own index sits chronologically before T.
Question 4

What does embargo solve that purging's formula doesn't already cover?

Purging removes every mechanically computable overlap. Embargo is a further, deliberately conservative buffer for correlation a fixed window length doesn't fully capture.
Question 5

In the worked example (n=1,000, w=20, H=5, T=500, h=100), how many total days get purged before even adding the embargo?

Days 495-499 (5 rows) purge for the label leak; days 600-618 (19 rows) purge separately for the feature leak. 5 + 19 = 24, before the embargo's further 10 days.
Section 11

What to carry forward

01

Random k-fold CV assumes exchangeable rows; time-ordered price data isn't — shuffling can literally train on the future and grade on the past.

02

Walk-forward validation fixes the obvious leak: Train_k uses only i < T_k, Test_k only the strict future window right after it, and the boundary rolls forward one fold at a time.

03

A clean split date is necessary but not sufficient — rolling feature windows and forward-looking labels can straddle the boundary and leak test-period information into training anyway.

04

Purging removes every training row whose combined feature-and-label window overlaps the test interval — a computable rule, not a judgment call.

05

Embargo adds a further, deliberately conservative buffer after the test window, for serial correlation no fixed window length fully captures.

06

Passing a purged, embargoed OOS test doesn't prove edge — it only makes the OOS number honest. This repo's own scripts still run every fold without a purge or embargo gap, which is a checkable next step, not a disqualifying flaw.

What this now lets you do

Read any OOS or backtest split — in this repo or anywhere else — and ask the two questions that actually matter: is the split chronological, and do any feature or label windows straddle the boundary? Compute exactly which training rows a given w, H, and boundary date require purging, and size an embargo deliberately instead of skipping it.
